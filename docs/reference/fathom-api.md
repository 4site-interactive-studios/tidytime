# Fathom API (meetings & transcripts)

Read-only reference for pulling Fathom-recorded meetings, their calendar invitees, and
speaker-labeled transcripts into TidyTime's `meetings` / `meeting_invitees` /
`transcript_utterances` tables. Fathom's **recording** start/end is ground truth for meeting
duration.

## At a glance

| Thing | Value |
|---|---|
| Base URL | `https://api.fathom.ai/external/v1` |
| Auth header | `X-Api-Key: <key>` (Bearer OAuth also exists; v1 uses the key) |
| Key source | Fathom **User Settings → API Access** (generate key) |
| Key scope | The key owner's recordings **plus meetings shared with them** |
| Endpoint we use | `GET /meetings` |
| Incremental cursor | `created_after` (filters on Fathom `created_at`, not meeting start) |
| Page cursor | request `cursor=…`, response `next_cursor` |
| Rate limit (standard) | 60 requests / 60 s |
| Rate limit (heavy) | 30 requests / 60 s — can drop to **5 / 60 s** under platform load |
| Poll cadence (v1) | every ~10 min (see [polling](#polling--incremental-sync)) |
| Writes to | `meetings`, `meeting_invitees`, `transcript_utterances`; cursor in `sync_state` |
| Consuming phase | [Phase 3](../phases/phase-3-meetings-calendar.md) |

TidyTime issues **GET only** against Fathom. There is no product reason to POST/PATCH; keep the
client read-only for the same architectural reason Productive is (see
[../guardrails.md](../guardrails.md) — G1 is Productive-specific, but the read-only posture is
uniform across ingest).

## Authentication

Every request carries the API key in the `X-Api-Key` header. The key is generated by the user
in **Fathom User Settings → API Access** and pasted during setup; it is stored in the macOS
**Keychain** via `SecretStore`, never in `config.json`, the DB, logs, or fixtures
([../guardrails.md](../guardrails.md) — G6).

```http
GET /external/v1/meetings?include_transcript=true&include_summary=true HTTP/1.1
Host: api.fathom.ai
X-Api-Key: fathom_sk_live_xxxxxxxxxxxxxxxxxxxxxxxx
Accept: application/json
```

- **Scope:** the key resolves to a single Fathom user. It returns that user's own recordings and
  any meetings explicitly shared with them — exactly the set TidyTime wants for one operator.
- **401** on a missing/invalid key. Surface this in `doctor` as "Fathom: key invalid" rather than
  failing sync silently.
- ⚠️ **Build-time check:** confirm the exact key prefix/format when the real key is generated; the
  `fathom_sk_live_…` shape above is illustrative.

## Rate limits

| Class | Limit | Applies to |
|---|---|---|
| Standard | 60 requests / rolling 60 s | list calls without transcript/summary |
| Heavy | 30 requests / rolling 60 s | recordings endpoints, and `/meetings` with `include_transcript` **or** `include_summary` |
| Heavy under load | as low as **5 requests / 60 s** | Fathom may throttle heavy calls further during high platform activity |
| OAuth (n/a to v1) | 60 requests / 60 s per app | token endpoint only |

Every TidyTime poll requests transcript + summary, so **treat every `/meetings` call as a heavy
call**. Practical consequences:

- Run the Fathom sync **serially** (concurrency 1). Do not fan out one request per meeting.
- On **429**, back off and retry with jitter; respect any server-requested delay if present, else
  start at ~5 s and double. A 10-minute poll cadence leaves ample headroom even at the 5/60 s floor.
- Paging through a backlog (first run) can burn the heavy budget fast; **persist each page and let
  the next poll continue from the stored cursor** rather than draining the limit in one pass.

**Limits re-verified 2026-08-28** — unchanged. Verbatim from
<https://developers.fathom.ai/api-overview>: "you are able to make a maximum of 60 calls to the API
in a 60 second window"; heavy calls are "30 in a 60 second window… during periods of elevated
activity this limit may be adjusted down to 5 every 60 seconds."

✅ **Build-time check resolved (2026-08-28): Fathom sends NO `Retry-After` header.** A live probe of
`api.fathom.ai` returns the IETF `RateLimit-*` family instead:

```
HTTP/2 429
ratelimit-limit: 60
ratelimit-remaining: 0
ratelimit-reset: 0
```

Two consequences a client must handle, both of which bit this codebase:

1. **Read `RateLimit-Reset`, not just `Retry-After`.** A client that only looks for `Retry-After`
   gets `nil` from Fathom every time and silently falls back to its own (much shorter) delay while
   believing it is honoring the server.
2. **Look headers up case-insensitively.** Over HTTP/2 header names are lowercase on the wire, so
   `headers["Retry-After"]` misses `retry-after`. Use `HTTPResponse.serverRequestedDelay`, which
   handles both the casing and the header-family difference.

> **A 429 on every run for days is not a rate-limit problem.** The window is 60 seconds; a
> 15-minute poll cadence clears it ~14 minutes before the next run. Continuous 429s across days
> mean the run is re-requesting the same pages each time — i.e. it is discarding progress and
> replaying — or the key itself is refused. Tuning the backoff will not fix either, and shipping
> such a change hides the real fault. See DECISIONS.md item 4.

## `GET /meetings`

Lists meetings newest-relevant first, with optional embedded transcript and summary.

### Query parameters

| Param | Type | Use in TidyTime |
|---|---|---|
| `created_after` | ISO-8601 string | **Incremental cursor.** Filters to meetings whose Fathom `created_at` is after this instant. Store the max `created_at` seen in `sync_state.cursor`. |
| `created_before` | ISO-8601 string | Not used in v1 (backfill window if ever needed). |
| `cursor` | string | Pagination cursor; pass back the previous response's `next_cursor`. |
| `include_transcript` | boolean | `true` — we need speaker-labeled utterances. |
| `include_summary` | boolean | `true` — populates `meetings.summary`. |
| `include_action_items` | boolean | Not v1 (leave default `false`). |
| `include_highlights` | boolean | Not v1. |
| `include_crm_matches` | boolean | Not v1. |
| `calendar_invitees_domains[]` | array | Optional server-side filter by invitee domain; v1 pulls all and classifies locally. |
| `calendar_invitees_domains_type` | enum | `all` \| `only_internal` \| `one_or_more_external`. Not used in v1. |
| `recorded_by[]` | array | Emails of recording users; not used in v1. |
| `teams[]` | array | Team-name filter; not used in v1. |
| `meeting_type` | string | Meeting-type-name filter; not used in v1. |

### Example request

```bash
curl -sS 'https://api.fathom.ai/external/v1/meetings' \
  --get \
  --data-urlencode 'created_after=2026-07-22T00:00:00Z' \
  --data-urlencode 'include_transcript=true' \
  --data-urlencode 'include_summary=true' \
  -H 'X-Api-Key: '"$FATHOM_KEY" \
  -H 'Accept: application/json'
```

### Response envelope

```json
{
  "limit": 25,
  "next_cursor": "eyJwYWdlX251bSI6Mn0=",
  "items": [ /* Meeting objects */ ]
}
```

- `items` is the array of meetings.
- `next_cursor` is a string when more pages exist, `null`/absent on the last page. Loop:
  `while next_cursor { fetch with cursor=next_cursor }`.
- `limit` echoes the page size the server applied.

## Field mapping → data model

Column names are exactly those in
[../architecture/data-model.md](../architecture/data-model.md). Timestamps arrive as ISO-8601
strings and are stored as **INTEGER Unix epoch seconds, UTC**
([../../CLAUDE.md](../../CLAUDE.md) conventions).

### `meetings` (one row per `items[]`)

| `meetings` column | Source field | Notes |
|---|---|---|
| `id` | `String(recording_id)` | Fathom recording id, stringified → PK. Re-sync is an upsert. |
| `source` | — | Literal `'fathom'`. |
| `title` | `title` (fallback `meeting_title`) | `meeting_title` is the raw calendar event title. |
| `scheduled_start` | `scheduled_start_time` | Parse ISO-8601 → epoch. |
| `scheduled_end` | `scheduled_end_time` | Parse ISO-8601 → epoch. |
| `recording_start` | `recording_start_time` | **Ground truth start.** |
| `recording_end` | `recording_end_time` | **Ground truth end.** |
| `duration_seconds` | `recording_end - recording_start` | Fall back to `scheduled_end - scheduled_start` if recording bounds are null. |
| `has_transcript` | `transcript != null && !empty` | |
| `has_summary` | `default_summary != null` | |
| `summary` | `default_summary.markdown_formatted` | Always English per Fathom. |
| `external_url` | `share_url` | The shareable Fathom URL (`url` is the internal call URL). |
| `calendar_event_id` | — | **Not in the Fathom payload.** Resolved by TidyTime's own match to `calendar_events` (by time window + attendee overlap / `ical_uid`), Phase 3. Leave `NULL` until matched. |
| `fetched_at` | — | `Clock.now`. |
| `created_at` | — | Row insert time (our own; distinct from Fathom `created_at`, which drives the cursor). |

### `meeting_invitees` (one row per `calendar_invitees[]`)

| `meeting_invitees` column | Source field | Notes |
|---|---|---|
| `meeting_id` | parent `meetings.id` | |
| `email` | `calendar_invitees[].email` | Nullable. |
| `name` | `calendar_invitees[].name` | Nullable. |
| `email_domain` | `calendar_invitees[].email_domain` | **Pre-parsed by Fathom** — no need to split the address. Strong client signal. |
| `is_external` | `calendar_invitees[].is_external` | `0`/`1`. `true` = outside the recorder's org → likely a client contact. |

`matched_speaker_display_name` (present on the invitee) is not stored; it's the same linkage the
transcript exposes via `speaker.matched_calendar_invitee_email`.

### `transcript_utterances` (one row per `transcript[]` item, in array order)

| `transcript_utterances` column | Source field | Notes |
|---|---|---|
| `meeting_id` | parent `meetings.id` | |
| `idx` | array index (0-based) | Preserves order; the index for `ORDER BY`. |
| `speaker` | `transcript[].speaker.display_name` | Human label. |
| `speaker_email` | `transcript[].speaker.matched_calendar_invitee_email` | Nullable; links the utterance to an invitee (and thus a domain → client signal). |
| `start_seconds` | parse `timestamp` (`HH:MM:SS`) → seconds | Offset **from `recording_start`**. `"00:14:03"` → `843.0`. |
| `end_seconds` | — | **Not provided per-utterance.** Store `NULL`, or derive as the next item's `start_seconds` if the splitter needs a bound. |
| `text` | `transcript[].text` | The utterance. |

**Timestamp parse helper** (offset seconds, matches `start_seconds REAL`):

```swift
/// "HH:MM:SS" (offset from recording_start) → seconds. Fathom omits fractional parts.
func offsetSeconds(_ hms: String) -> Double? {
    let p = hms.split(separator: ":").compactMap { Double($0) }
    guard p.count == 3 else { return nil }
    return p[0] * 3600 + p[1] * 60 + p[2]
}
```

## Duration is the recording, not the calendar

Guardrail for the suggestion engine's meeting split
([../architecture/suggestion-engine.md](../architecture/suggestion-engine.md)): a meeting's real
length is `recording_end_time - recording_start_time`, **not** the scheduled slot. In the sample
above the calendar booked 60 min (17:00–18:00) but the recording ran 17:02:18 → 18:03:11 ≈ **60m
53s**. Transcript segments produced by the classification ladder are mapped back to
`transcript_utterances.start_seconds` (offset from `recording_start`), so per-client minute splits
reconcile against the recorded span, and any rounding is auditable to a timestamp range.

Meetings Fathom did **not** record won't appear here at all — those fall back to the Google
Calendar event (`meetings.source = 'calendar'`, `id = 'cal:<eventid>'`) with attendee/title
signals only. See [./google-calendar-api.md](./google-calendar-api.md).

## Polling & incremental sync

v1 polls; the webhook is a later upgrade (below).

1. Read `sync_state.cursor` for `source = 'fathom'` (an ISO-8601 instant; empty on first run).
2. `GET /meetings?created_after=<cursor>&include_transcript=true&include_summary=true`.
3. Page with `cursor=next_cursor` until `next_cursor` is null (cap pages per run — see rate limits).
4. Upsert each meeting, its invitees (replace-all per meeting), and utterances.
5. Advance `sync_state.cursor` to the **max `created_at`** across fetched items; set
   `last_success_at`. On error, record `last_error` and keep the old cursor.

```sql
-- Cursor bookkeeping (source row is created in Phase 1).
UPDATE sync_state
   SET cursor          = :maxCreatedAtIso,   -- ISO-8601 of the newest created_at seen
       last_run_at     = :now,
       last_success_at = :now,
       last_error      = NULL
 WHERE source = 'fathom';
```

Why `created_after` filters on **`created_at`** and not the meeting's start matters: Fathom only
exposes a meeting once processing (transcription/summary) finishes, which **lags the meeting end
by minutes**. Cursoring on the processing time (`created_at`) means a late-processed meeting is
still caught on the next poll — cursoring on `scheduled_start_time` would silently skip it.

⚠️ **Build-time check:** confirm `created_after` is **exclusive** (strictly after) vs inclusive.
If inclusive, the newest already-synced meeting will re-appear each poll — harmless because
upserts are idempotent, but store the cursor accordingly to avoid needless re-fetches.

## Sensitivity & retention (guardrails)

- **G2 — sensitivity gate.** Transcripts are the highest-sensitivity content TidyTime touches. No
  transcript text, summary, or invitee data reaches a **cloud** rung (Fireworks/Anthropic) until
  it passes the local `SensitivityGate`. A meeting flagged sensitive (flagged participant, or
  personnel/comp/legal keywords) resolves to a generic task with a bland note and is never placed
  in an outbound payload. The gate **fails closed**. See [../guardrails.md](../guardrails.md).
- **G9 — retention.** `transcript_utterances` are raw sensitive rows and **purge after the
  retention window** (default 90 days). The `meetings` summary row is kept (distilled artifact);
  only the utterances age out. Retention job: [Phase 1](../phases/phase-1-capture.md), enforced
  ongoing.

## Webhook (later upgrade, not v1)

Fathom exposes a webhook ("new meeting content ready") registered via `POST /webhooks`, which
would replace polling with push once TidyTime has a reachable receiver. It is explicitly a
**post-v1** optimization ([../../PLAN.md](../../PLAN.md) §13); v1 ships the 10-minute poll above.
The `IngestSource` protocol seam ([../architecture/module-map.md](../architecture/module-map.md))
is where a webhook receiver later drops in behind the same `sync()` contract.

⚠️ **Build-time check:** the exact webhook event name, `POST /webhooks` payload schema, and
signature-verification header were **not** re-verified against vendor docs for this write-up
(the list-meetings and overview pages were). Confirm all three when the webhook path is actually
built.

## Testing

Per [../build/testing-strategy.md](../build/testing-strategy.md), the Fathom client sits behind a
protocol and unit-tests run against **recorded fixtures** — no live network. Capture one real
`GET /meetings` response (transcript + summary) into `Tests/Fixtures/fathom/meetings.json`,
**scrub the `X-Api-Key`** and any real personnel content, and assert:

- ISO-8601 → epoch parsing for all four time fields.
- `duration_seconds` = recording span, with scheduled fallback when recording bounds are null.
- `HH:MM:SS` → `start_seconds` (e.g. `"00:01:05"` → `65.0`).
- invitee `email_domain` / `is_external` land verbatim in `meeting_invitees`.
- pagination loop terminates on `next_cursor = null`.
- cursor advances to the max `created_at`, not to a meeting `scheduled_start_time`.
