# Module map

**Status:** canonical (source of truth for target names & dependency rules) ·
**Last reviewed:** 2026-07-23

TidyTime's logic lives in one local SwiftPM package, **`TidyKit`**
(`Packages/TidyKit/`), split into eight library targets. The Xcode app target
(`App/`, generated by XcodeGen) is a thin shell that owns `@main`, the Info.plist,
entitlements, and signing — the things SwiftPM can't express. See
[../build/xcodegen-spec.md](../build/xcodegen-spec.md).

## Targets & responsibilities

| Target | Responsibility | Builds in |
|---|---|---|
| **TidyCore** | Domain models (the GRDB records), `Config` loading, `SecretStore` (Keychain), `TidyLog` (os.Logger), time/rounding utilities, shared errors, protocol definitions used across layers. No I/O of its own. | 0 |
| **TidyStore** | GRDB setup (WAL, PRAGMAs), the `DatabaseMigrator`, DAOs / query helpers, the retention job. Owns the schema in [data-model.md](data-model.md). | 0 |
| **TidyCapture** | On-device capture: `NSWorkspace` app watcher, Accessibility window-title reader, `BrowserAdapter` (Chrome impl), idle/away via `CGEventSource`, sleep/lock notifications, meeting-state inference. Writes `activity_samples`/`page_snapshots`/`away_gaps`. | 1 |
| **TidyIngest** | Read-only API clients + sync engines for Productive, Fathom, Google Calendar, Slack; incremental sync via `sync_state`; rate-limit handling. Each client behind a protocol for fixture-based testing. | 2–4 |
| **TidyUnderstand** | Sessionization, entity resolution / the client registry, the classification ladder's local rungs (rules + lexical), the **sensitivity gate**, the learning loop. Consumes capture + ingest, writes `sessions`/`entity_signals`. | 5 |
| **TidyAI** | The provider **router**, the on-device (Foundation Models) rung, the Fireworks and Anthropic clients, the **usage ledger** (`ai_calls`), budget caps. The only place cloud calls happen; every call is gated and metered. | 6 |
| **TidySuggest** | Suggestion engine: 15-min rounding + round-up bias, micro-work pools, meeting splitting, gap analysis vs. `pd_time_entries`, new-task proposals. Emits `suggestions`. | 5–6 |
| **TidySurface** | Reusable SwiftUI: menu bar popover, nudge presenter, away prompt, recap window (timeline + card stack), dashboard, settings. View-models read from `TidyStore`/`TidySuggest`. | 0 (shell) → 5–6 (full) |

The app target, **TidyTimeApp** (`App/`), wires these together: `MenuBarExtra` scene,
dependency container, app lifecycle, `SMAppService` launch-at-login, permission prompting,
and the `doctor` debug view.

## Dependency graph (must stay acyclic)

```
                 ┌─────────────┐
                 │  TidyCore   │  ← models, Config, Keychain, logging, protocols
                 └─────┬───────┘
        ┌──────────────┼───────────────┬───────────────┐
        ▼              ▼               ▼               ▼
   ┌─────────┐   ┌───────────┐   ┌───────────┐   ┌────────┐
   │TidyStore│   │TidyCapture│   │TidyIngest │   │ TidyAI │
   └────┬────┘   └─────┬─────┘   └─────┬─────┘   └───┬────┘
        │              │               │             │
        │        (all write via TidyStore DAOs)      │
        └──────────────┴───────┬───────┴─────────────┘
                               ▼
                       ┌───────────────┐
                       │TidyUnderstand │  (uses TidyStore; may call TidyAI router)
                       └───────┬───────┘
                               ▼
                        ┌────────────┐
                        │TidySuggest │  (TidyStore + TidyUnderstand + TidyAI)
                        └─────┬──────┘
                              ▼
                       ┌────────────┐
                       │TidySurface │  (TidyStore + TidySuggest read models)
                       └─────┬──────┘
                             ▼
                      ┌──────────────┐
                      │ TidyTimeApp  │  (App/ — depends on everything, wires it up)
                      └──────────────┘
```

**Rules:**
- `TidyCore` depends on nothing internal. Everything may depend on `TidyCore`.
- Capture, Ingest, AI do **not** depend on each other; they meet only through `TidyStore`
  (data) and `TidyCore` (protocols/models). This keeps the pipeline testable a stage at a time.
- `TidyUnderstand` and `TidySuggest` orchestrate; they may call the `TidyAI` router but must
  degrade gracefully when it's unavailable (budget cap tripped, Apple Intelligence off).
- `TidySurface` is presentation only — no capture, no network, no direct provider calls.
- No target imports `TidyTimeApp`.

## Protocol seams (the extension points)

These are the boundaries that let v1 stay small and v2/teammate features land without
surgery. Define the protocol in `TidyCore` (or the owning target) and inject implementations.

| Protocol | Purpose | v1 implementation | Later |
|---|---|---|---|
| `BrowserAdapter` | Active-tab URL/title/page-text | `ChromeAdapter` (AppleScript) | Safari/Firefox/Dia via WebExtension + native messaging |
| `AIProvider` | One classify/generate call | `AppleOnDeviceProvider`, `FireworksProvider`, `AnthropicProvider` | new models = config, not code |
| `ProductiveClient` (read) | GET-only Productive access | `LiveProductiveClient` | **v2:** a separate write client, never bolted onto this one (guardrail G1) |
| `IngestSource` | `sync()` + cursor mgmt | one per source | Fathom webhook receiver replaces polling |
| `SecretStore` | token get/set | `KeychainSecretStore` | — |
| `Clock` | injectable time | system clock | deterministic clock in tests |
| `SensitivityGate` | screen content before cloud | `KeywordSensitivityGate` | richer models later |

## Testability

Every target ships a matching test suite in `Packages/TidyKit/Tests/`. Because I/O sits
behind protocols, unit tests run with **recorded fixtures** and an in-memory GRDB database —
no live network, no live Accessibility. The guardrail tests (see [../guardrails.md](../guardrails.md))
live here too. Details: [../build/testing-strategy.md](../build/testing-strategy.md).
